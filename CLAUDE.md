# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Deployment scripts and config for a home LLM server: no build system, no tests. The machine has two AMD Radeon AI PRO R9700 cards (gfx1201, 32 GB each), 121 GB RAM, boots to TTY, and runs one model at a time, Qwen3.8-Flash-Next IQR-V4 (refusal control vector per request) or Qwen3.8-27B IQ8R (`RADIANCE_PROFILE` in `rad/config.env` says which), on the **radiance** engine (`codeberg.org/StillDeadcode/radiance`, C++/HIP, `.rad` model containers, Docker image `stilldeadcode/radiance`). radiance is a separate engine from `vllm-radiance` (a patched vLLM image; the removed vLLM stack ran `magiccodingman/vllm-radiance`, a repackaging of `codeberg.org/StillDeadcode/vllm-radiance`). Both come from StillDeadcode and share the `libr4d` gfx1201 kernels; radiance drops vLLM/PyTorch.

The llama.cpp, vLLM, ASR/TTS and reranker stacks were removed on 2026-10-12. Do not reintroduce them, or reference their scripts as if they existed; history is in git and in `hindsight/experiments/`.

## Architecture

- `cicero-rad.service` (systemd user unit) → `rad/run.sh` → Open WebUI on `:3000` plus `docker compose up` of `rad/compose.yaml` (radiance on `:8080`, model id `qwen-local` whichever profile is loaded). `run.sh` exits when either child dies; systemd restarts the whole stack. Both log to `logs/rad.log`.
- The unit runs as the user. `run.sh` and `update.sh` re-exec under `sg docker` when the login session predates the user's `docker` group membership.
- **Model profiles:** each profile (`flashnext`, `27b`) is `rad/profiles/<name>.env` (model file, HF repo + pinned revision) plus `<name>.yaml` (the model entry's own engine keys: aliases, TP, Flash-Next's `expert_tiered`/`host-pool-mib`, `control-vector`). `RADIANCE_PROFILE` in `rad/config.env` picks one; `./switch.sh <name>` downloads it if missing, sets it and restarts the stack. Both models fill both cards, so they never run together.
- radiance 2.0 takes only `--config FILE`. `run.sh` writes `rad/state/radiance.yaml`: `server:` from `config.env` (host/port), then `rad/radiance.yaml` (keys every profile shares: `memory:`, `scheduler:`, and `defaults:` for context, KV dtype, prefix cache), then one `models:` entry named `SERVED_MODEL_NAME` with the profile's keys. `rad/compose.yaml` mounts it at `/etc/radiance/radiance.yaml`. `rad/config.env` also holds the image tag, active profile and models dir; its paths are relative to the repo root.
- The prefix cache lives in VRAM plus a 16 GiB pinned host-RAM tier (`prefix-cache-mib` 16384, ~1.14M tokens of Flash-Next context, idle TTL 3600 s); a restart loses it. Between turns the idle KV VRAM is lent to the experts, so returning conversations come mostly from the host tier. Flash-Next is hybrid: a hit also needs a linear-state snapshot from the shared store (`checkpoint-slots` 120 × 112.73 MiB pinned; `auto` gave 80), and without one the cached attention blocks are recomputed. On 2026-11-15 both the 8 GiB tier and the 80 slots ran full under the LAN agent (140K-token main conversation, many 5–8K subtask sessions) plus a Hindsight validation run, which pushed the agent's conversation out (one 131K turn re-prefilled in 55 s); both were raised then. `/sessions` and `/stats` show occupancy, `host_drops`, snapshot `store_full` evictions and `no_snapshot` hit cuts. Upstream removed the SSD tier in 1.5.0 (issue #70). `rad/state/` (gitignored) holds the generated config and ad-hoc bench files.
- `models/radiance_v2/` holds the 2.0 model files (gitignored; Flash-Next IQR-V4 113.3 GiB, 27B IQ8R 28.76 GiB). `models/rad/` still holds the 1.x FP8 containers, which 2.0 refuses. `rad/fetch-model.sh` downloads only when the file is missing. Upstream replaces `.rad` files under the same name, so each profile pins `RADIANCE_MODEL_REVISION`; taking a new revision means updating it and deleting the file.
- `gpu-power/` — root system unit `cicero-gpu-power.service` caps both cards' PPT0 at 250 W (`GPU_POWER_CAP_W`, 210–300) on every boot; the cap does not survive a reboot otherwise. `sudo gpu-power/install.sh` installs a root-owned copy of `set-power-cap.sh`; re-run it after editing either file.
- `hindsight/` — the Hindsight memory server's docs, updater, Control Plane unit and end-to-end benchmark. Hindsight sends all LLM calls to `:8080`; its reranker runs on `seneca.local` because radiance leaves no VRAM. `hindsight/experiments/` is history.

**Script flow:**
- `install.sh` (sudo): apt (Docker, pipx) → `amd-smi` check → `gpu-power/install.sh` → `docker` group → `hf` CLI + Open WebUI (Python 3.11 via uv) → linger → `rad/install-service.sh`
- `update.sh [tag]`: optionally re-pin the tag in `config.env` → `docker pull` → active profile's model download if missing → `rad/install-service.sh` → restart
- `switch.sh [profile]`: no argument lists profiles; otherwise `rad/fetch-model.sh` → set `RADIANCE_PROFILE` → restart
- `rad/install-service.sh`: disables and deletes the legacy units (`cicero-home-ai`, `cicero-vllm`, `cicero-tts-server`, `cicero-asr-proxy`, `cicero-vulkan*`), installs `cicero-rad.service` with paths rewritten to the repo location, enables it.

## Engine facts (radiance 2.0.0)

Measured on the `flashnext` profile (IQR-V4) on 2.0.0, switched 2026-11-15, unless noted. The `27b` profile passes `--check` on 2.0 but has not been started on it; its FP8 predecessor was quick-benchmarked on 1.2.3 only (decode 85/234 tok/s at 1/4 streams, prefill 2.8K tok/s).

- **Host:** the image is built on ROCm 10.1, so the host's amdgpu driver must support it (31.50 or 31.60; 31.60 installed 2026-10-12, runs 2.0.0). Resizable BAR must be on (both cards expose 32 GiB), and since 1.15.0 so must amdgpu's CWSR (`cwsr_enable=1`, the default; startup refuses otherwise). Both cards sit behind PCIe 16 GT/s x8 slots, which bounds expert streaming and prefill. Each startup prints a `STARTUP REPORT` (each option with its source: YAML path or `auto`) and a `FINDINGS` report in `logs/rad.log`, then `model qwen-local: ready` (30 s after a restart with the file in the page cache). `/health` reports the process and each model's state; `/health?model=qwen-local` that model. A GPU memory fault exits the server (status 70) and systemd restarts it.
- **Containers:** 2.0 refuses any container with block-FP8, MXFP4, NVFP4 or ParoQuant weights, naming the first one; that is every 1.x container in `models/rad/`. No int8 build of the abliterated Flash-Next exists, so the control vector replaces it.
- **Memory:** both cards end up ~99% full: 3.2 GiB static weights, 17.3 GiB experts, 9.04 GiB KV per card (`kv-cache-dtype: i8`; 4.4 full-length sessions at 262144); the token embedding sits in pinned RAM (`embedding-placement: ram`, the default). Experts that do not fit stream from a pinned host pool: since 2.0 `host-pool-mib` is the total for both cards, so 24576 gives 12.59 GiB per card as 1.x's 12288 per card did. `ngram-placement: auto` puts the 47.7 GiB n-gram table in pinned RAM (copied in 12.6 s). Pinned RAM totals ~102 GiB (n-gram 47.7, expert pool 24, embedding 1.2, prefix host tier 16, snapshots 13.2), above 2.0's default cap of 75% of RAM, so `memory.host-mib` is 108544; ~112 GB RAM in use while serving, ~8 GB available (was ~20 GB with the 8 GiB tier and 80 slots). Raising the host pool frees VRAM for the KV cache. Nothing else GPU-bound can run alongside it.
- **Where things landed is in the log:** read the `placement:`, `VRAM budget` and `kv:` lines of the latest startup in `logs/rad.log` before claiming anything about placement, memory or KV capacity.
- **Configuration:** the server takes only `--config FILE`; a 1.x command line is refused with the equivalent YAML printed, and `rad-yaml FLAGS…` in the image prints it without starting (it copies `host-pool-mib` without halving it into the 2.0 meaning). `--check` validates a file without serving: `docker run --rm -v $PWD/models/radiance_v2:/models:ro -v <file>:/etc/radiance/radiance.yaml:ro stilldeadcode/radiance:2.0.0 --config /etc/radiance/radiance.yaml --check`. An unknown key or a key at the wrong level is refused. `served-model-name` is gone: the entry's name is the model id. `kv-cache-dtype` takes `bf16` or `i8` (`fp8` is GLM-5.3-Flash's alone). `gpu-headroom-mib` stays 256 (1.x needed ≥ ~226; 2.0's default is 96, untested here). YAML has no environment-variable expansion except `server.api-key-env`.
- **Control vector:** `control-vector: off` (in `flashnext.yaml`) loads the image's `qwen4exp-control-vector.gguf` (Cudecnik's refusal projection, layers 4..44, scale 1) and leaves requests off, so `qwen-local` (Hindsight, the LAN client, Open WebUI's base model) is the stock model; a request opts in with `"control_vector": true`. radiance cannot attach the switch to a model name (an alias has no settings of its own; a second entry would load the model twice), so the "uncensored" model exists only in Open WebUI: a workspace model `qwen-local-uncensored` on `qwen-local` with custom parameter `control_vector` = `true` (stored in Open WebUI's database, not in this repo). `POST /admin/control-vector {"enabled": bool}` from loopback changes the default until restart; `GET` shows it. Conversations with and without the vector are cached apart. Upstream measured `off` as identical to the stock model and `on` at ~2% slower decode with speculation off. `attn-prefill-fp8` (1.11.0) has kernels only for the 27B's attention and refuses to start on Flash-Next.
- **1.x flag findings** (same names as 2.0 keys, not re-tested on 2.0): `--draft-coupling on` (1.12.0) helps Flash-Next's MTP at high temperature and costs at low. `--weight-prefetch` (1.13.0) is on by default. `--expert-profile`/`--expert-pin-top`/`--draft-expert-placement host` (1.14.0) choose which routed experts stay in VRAM; tested 2026-10-31 on 1.15.0 and rejected: a decode profile and a fully static layout matched the heat engine, and `--draft-expert-placement host` cost 22% at 4 streams for +8% prefill. In 1.15.0 `--expert-pin-top` pins every resident expert whatever F is (threshold = share − 1.0), which turns the heat engine off.
- **API fields** (checked on 1.x; `reasoning_efforts` in `/v1/models` matches on 2.0): since 1.12.0 `DELETE /sessions/<label>` forgets one stored conversation. Since 1.4.0 an unknown request field is ignored without an error or a log line (1.2.3 refused it with HTTP 400), and an OpenAI `reasoning` object is accepted. `reasoning_effort` accepts `none`, `minimal`, `low`, `medium`, `xhigh`; `high`/`max` are still refused with HTTP 400.
- **Model id:** since 2.0 a request must name `qwen-local` or one of the profile's `aliases` (`qwen3.8-flash-next`, `qwen3.8-27b`); any other name gets 404 (1.x served any name; 4,568 logged requests used `qwen3.8-flash-next`, hence that alias). A request without `model` goes to the only model. `/v1/models` lists the entry and its aliases with `state`, `capabilities` and `max_model_len`, and to loopback callers only (no API key here) `root`, the loaded `.rad` file, so a local client can tell the profiles apart. Every profile is served under that id, so `llm_requests` rows, Open WebUI chats and bench results do not say which model answered: attribute them by timestamp against the dated `rad: … profile <name>` start lines in `logs/rad.log`.
- **Endpoints:** `/v1/chat/completions`, `/v1/completions`, image and video input; since 1.3.0 also `/v1/responses`, Anthropic `/v1/messages`, llama-server's `/completion`, `/infill` and `/props`, and logprobs. `/v1/embeddings` serves embedding models only, so neither profile has it.
- **Baseline** (`rad/bench-openai.py`): full run on 1.2.3 (2026-10-07, driver 31.50): decode 121 tok/s single stream, 212/316/448 aggregate at 2/4/8; prefill 3.6–4.2K tok/s; 15/15 tool calls. Quick run on 1.4.0 (2026-10-12, driver 31.60, `--conc 1,4 --reps 4 --prefill 16384`): 143/308 aggregate at 1/4, prefill 4.6K tok/s, 15/15 tool calls; the same quick run on 1.2.3 with driver 31.60 gave 4-stream 291–295, so 1.4.0 is +5% there and +14% on prefill. Prefill prompts come from Python's stdlib source, so numbers taken before 2026-10-12 used different text. Full run on 1.13.0 (2026-10-27, `flashnext-uncensored`): 122/215/310/474 aggregate at 1/2/4/8, prefill 4.1–4.6K tok/s, mixed 25K prefill 6.6 s with the decode stream at 62 tok/s, 15/15 tool calls; the quick run gave 155/324 and 4.66K (1.10.0: 139/327, 4.42K). Full run on 1.15.0 (2026-10-31): 131/219/310/476, prefill 4.6–4.7K (the 4K prompt +16% over 1.13.0), mixed 6.5 s / 65 tok/s, 15/15; quick 150/335, 4.72K. Quick run on 1.17.0 (2026-11-11, first run after the restart): 143/304, 4.77K, mixed 6.4 s / 67 tok/s, 15/15; a same-day A/B (both right after a restart) gave 1.15.0 145/321, 4.72K, so 1.17.0 is ~4% slower at 4 streams (three runs 304–310) and level at 1 stream and on prefill. Full run on 1.17.0 (2026-11-15, after three days' uptime; the last 1.x baseline, since 2.0 refuses FP8 containers): 132/201/296/458, prefill 4.72–4.77K, mixed 6.6 s / 63 tok/s, 15/15; quick 148/301, 4.85K, mixed 6.4 s / 66 tok/s. Its prefill was re-run (labels `…-prefill-r2`) because a LAN request overlapped the first pass. Full run on 2.0.0 with the IQR-V4 container and the control vector on (2026-11-15, right after the switch): 165/254/327/483 (+25/+26/+10/+5% over 1.17.0), prefill 5.09–5.27K (+8–11%), mixed 6.5 s / 139 tok/s, 15/15; quick 161/340, 5.25K, mixed 6.8 s / 116 tok/s. The 4-stream decode and the quick mixed were re-run (labels `…-c4-r2`, `…-quick-mixed-r2`) after LAN overlaps; the overlapped 4-stream pass had read 348. Engine and model changed together, so these numbers do not separate the two. With `--reps 3` the `reason` prompt is never run, so the full run's 1-stream median is lower than the quick run's; compare like with like.

## Key conventions

- **Pin the image tag**; never `latest`. Releases land several times a day. Change it only through `./update.sh <tag>`, then re-run `rad/bench-openai.py` and compare with the baseline.
- **Stop other clients before benchmarking.** Open WebUI and Hindsight share `:8080`; check `hindsight.service` and in-flight requests in `logs/rad.log` first. A LAN client (192.168.68.54) also calls `:8080`, including an agent sending streamed 80–140K-token tool-call prompts; count both `req … chat from` and `req … chat stream from` lines not from 127.0.0.1 during each run and discard runs it overlapped. Long Hindsight validation runs (50–130K-token Reflect prompts) compete with that agent for prefill and evict its prefix cache, so run them when it is idle.
- Keep config comments to one or two lines of fact; rationale belongs in `README.md` or `hindsight/experiments/`.
- Deployment glue goes in `rad/`; do not keep files inside a cloned upstream tree.
- **Validate any Hindsight LLM change against a large bank, with enough repetitions.** Run `hindsight/benchmark/bench-hindsight.py` (disposable banks) and a read-only pass over the 1749-memory `psychology` bank. Small banks keep generations short and hide runaway-generation failures — `gemma4-26b-a4b-qat` passed every disposable-bank workflow and still hung Reflect on `psychology`. That failure hit ~8% of Reflects, so a 6-probe suite came back green about half the time. See `hindsight/experiments/gemma4.md`.
- **Hindsight's `llm_requests` table is the ground truth for workload shape** (`psql --dbname hindsight`: per-call `operation`, `input_tokens`, `cached_tokens`, `output_tokens`, `duration_ms`, full prompt). Query it before assuming request sizes. On the `psychology` bank: Retain ~2.4k prompt / ~600 generated, Consolidation ~5.5k / ~255 (77% of calls), Reflect 14k p50 / 38k max (7%); decode dominates. See `hindsight/benchmark/README.md`.
